# 💡 RoutinePlus: IsWorkday 系统级优化与迭代建议草案

本项目经过本次 `v1.2.0` 的重构，已经完成了核心的“日历日期覆盖”与“批量多选配置”，并且锁定了固定的 `debug.keystore` 签名库，在架构的离线优先高可用上已经具有了极高水准。

为了追求极致的产品力、在视觉和功能上将本 App 打造成三星生态下的 **Premium 级天花板插件**，我基于第一性原理，对整个 codebase 的架构设计、UI/UX 细节以及业务稳定性进行了深度剖析，特此提出以下优化方向与可选方案，供你后续迭代参考：

---

## 1. UI 与交互体验优化 (UI & UX Aesthetics)

### 1.1 日历手势滑动切月 (ViewPager Integration)
- **现状分析**：当前日历切换月份通常是通过点击顶部「上一月/下一月」按钮来完成的。在单手握持手机操作时，由于屏幕上方位置较远，频繁点击按钮略显生硬，缺乏呼吸感。
- **改进方案**：
  - 引入 Compose 官方的 `HorizontalPager`，将月份日历网格嵌套入 Pager 中。
  - 支持通过手势在日历网格区域左右阻尼滑动切月，并带有微妙的物理淡入淡出动效。
- **产品价值**：显著增加界面的“水灵感”和操作的流畅度，完美贴合三星 One UI 优雅的动画美学。

### 1.2 批量选择状态的全局震动微反馈 (Haptic Feedback)
- **现状分析**：长按或多选日历日期时，完全是纯视觉反应。由于日历单元格体积相对较小，单手操作容易漏触。
- **改进方案**：
  - 在点击或长按日历格（切换选中状态）时，调用 `LocalView.current.performHapticFeedback(HapticFeedbackConstants.KEYBOARD_TAP)` 触发极其轻微的线性马达震动反馈。
- **产品价值**：通过多感官联动，显著提升用户对多选边界的精准判断力。

## 2. 核心功能与健壮性迭代 (Feature Enhancements)

### 2.1 系统闹钟设置的“幂等性保护” (Idempotence & Anti-Flicker)
- **现状分析**：当前在三星“日常程序”每天自动触发调用 `SetAlarmUseCase` 时，系统会无条件在系统时钟中再次写入一次该时间的闹钟。如果在短时间内日常程序被误触重复运行，系统闹钟可能会被反复替换或闪烁。
- **改进方案**：
  - 在通过 `AlarmClock` 设置闹钟之前，首先利用三星/Android 系统的 `AlarmManager` 检测或本地状态判断（例如在 Room 或 DataStore 中缓存上一轮静默设置的精确时间与标签）。
  - 若检测到与即将设定的闹钟标签一致、且时间完全吻合，则**静默跳过创建**，仅弹出一个提示已设置的 Toast。
- **产品价值**：规避频繁重复唤起系统 AlarmClock Activity 可能带来的系统资源抖动，提高静默插件的绝对稳定性。

### 2.2 闹钟组支持 (Multi-Alarm Support)
- **现状分析**：当前仅支持全局设置一个时间段。而现实场景中，对于“重度赖床”用户或有多重阶段性安排的用户，可能需要多重保障（例如：`07:30` 预警闹钟 + `07:45` 强制起床闹钟）。
- **改进方案**：
  - 将全局配置的闹钟时间从单一的“小时/分钟”升级为“闹钟时间列表”。
  - 自定义日期覆盖（Override）时，也支持为该日期添加多段自定义时间。
  - 在 `SetAlarmUseCase` 中循环遍历，依次设置。
- **产品价值**：极大地拓宽了插件的用户受众，解决赖床群体的刚性痛点。

## 3. 架构健壮性与代码质量 (Architecture & Code Smells)

### 3.1 跨模块状态流防抖处理 (Flow Debouncing)
- **现状分析**：由于批量设置覆盖日期时，用户可能在毫秒级内连续快速点选日历格子。如果每一次状态变更都直接无防抖地触发底层 Room 的数据库持久化写入，在低配或老旧手机上可能会偶发短暂 UI 卡顿。
- **改进方案**：
  - 在 ViewModel 层中使用 Kotlin 协程的 `debounce(300ms)` 或者是利用批处理挂起函数对多选状态进行聚合。
  - 当用户在底部 Sheet 点击“保存”或者等用户停止连续点击 300ms 后，一次性批量执行 Room `INSERT / UPDATE` 事务，避免频繁数据库 I/O 开销。
- **产品价值**：在大批量复杂数据读写时，依然保持 App 的绝对零阻塞。

### 3.2 静默后台的超时自毁与防死锁机制 (Timeout & Auto-Finish)
- **现状分析**：后台执行入口 `ShortcutActivity` 必须对用户完全透明，它会静默读取 Room / DataStore，再设定系统闹钟。
- **改进方案**：
  - 在 `ShortcutActivity` 的 `onCreate` 异步启动协程中，除了原有的成功/失败后 `finish()`，额外增加一个 **5秒全局超时兜底逻辑**：
    ```kotlin
    lifecycleScope.launch {
        withTimeoutOrNull(5000) {
            // 执行 Room 读取和闹钟设定
        } ?: run {
            // 若 5 秒未响应（极端情况下 Room 卡死），强制 finish 自身，绝不让透明 Activity 驻留后台导致界面锁死
            finish()
        }
    }
    ```
- **产品价值**：保障了插件即使在极端数据库死锁或系统高负载挂起下，也绝不会引起手机桌面卡死或报错，保证系统级的安全系数。
